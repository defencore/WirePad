# WirePad agent instructions

WirePad is a browser-only editor published as a static GitHub Pages site. Keep the interface, catalog copy, and code comments in English. Preserve existing component IDs, pin IDs, and canvas pin positions so saved projects remain usable.

## Add and audit library components

1. Group related parts in a focused `src/catalog/families/catalog-*.js` module. Keep the part definition, illustration, footprint, and manufacturer CAD link together. Use a default `defineFamily(id, entries)` export, with each entry owning `{ component, render, footprint, model?, configuration? }`. Register each new family once in `src/catalog/catalog-families.js`; all consumers use `src/catalog/index.js`. Shared builders belong in `src/catalog/shared/`, not peer family modules. Large CAD data/artwork may be adjacent imported modules, with attribution and references retained. For a catalog-wide audit, split the work into named families, give agents separate files, and track which entries they checked.
2. Identify the exact part number, package, and board revision. Use the manufacturer's datasheet, pinout, photos, or mechanical drawings. Use a supplied photo for a matching unbranded variant. Record the reference URL on the entry and describe generic or unverified variants as representative.
3. Draw a self-contained SVG using the actual outline, connectors, controls, package, antenna, and relevant markings. Compare it visually with the reference from the same side. For connectors, distinguish the mating face from the solder side and confirm whether the view is mirrored. Put connection points directly on the corresponding physical pads or connector contacts, with labels immediately alongside them. Use clearly identified front/back or mating-face views for hidden contacts. Dense connectors may show physical contact numbers with full functions on hover; do not substitute distant logical pin banks for the module's physical layout.
4. Verify each exposed contact's printed label, electrical type, terminal number, and function. Define the stable canvas ID and derive its anchor and illustrated pad from the same physical contact coordinates. Use `surface: true` on contacts inside the drawing and `contactLayout: "physical"` on the component so wires remain visible above the board. Match KiCad symbol numbers to physical footprint pads, including repeated pads on one electrical terminal.
5. Use manufacturer land patterns and CAD files when available. Clearly label reference carriers, off-board terminations, and approximate geometry. Include a verified vendor STEP or CAD link where available.
6. Run `node --test` and `git diff --check`. Review both labeled and unlabeled SVGs, add representative parts on the canvas, and check an image export. Compare existing pin positions with the previous version after a visual audit. Open the generated symbol and footprint in native KiCad when available. For a release, verify the versioned build on the public domain.
7. Maintain [docs/COMPONENTS.md](docs/COMPONENTS.md) in the same change whenever components or families are added, removed, renamed, regrouped, or their KiCad/CAD scope changes. Update the explicit per-component assessments and evidence in [docs/catalog-kicad-accuracy.json](docs/catalog-kicad-accuracy.json), then run `node scripts/catalog.mjs` to automatically regenerate the complete category → manufacturer → source-family → component tree. Never edit the generated tree by hand. Use `FP:M` only for source-reviewed manufacturer geometry, `FP:C` for source-coordinate contact references, `FP:R` for reference/approximate/off-board carriers, and `FP:?` when evidence is missing; record the reason rather than guessing. A manufacturer CAD URL, a passing test or a successful KiCad import does not establish geometric accuracy. The current generated WRL models are approximate (`3D:A`); an external CAD link does not upgrade them. Do not let new entries inherit another component's assessment. Check freshness with `node scripts/catalog-tree.mjs --check` before completing the change.

## Architecture and verification

- Keep `model`, `geometry`, `catalog` and `assets` independent of DOM/UI/application controllers. Keep pure SVG generation separate from browser downloads and clipboard operations.
- Keep large catalog collections in focused specification sections with adjacent CAD/artwork and source attribution. Preserve explicit family ordering; do not grow a single giant specification array or inline artwork into controller code. Consumers outside the catalog use its public index.
- Use the shared geometry, endpoint, contact-number and project-limit helpers. Register configurable-part normalization/building in the catalog descriptor and its controls in the Inspector configuration provider; do not add component-ID branches to the editor or project parser.
- Every mounted controller must release listeners, observers, timers and DOM layers through its lifecycle scope. Keep application composition explicit and support destroy/remount.
- Run `node scripts/catalog.mjs` after catalog changes; it validates the catalog and refreshes `docs/COMPONENTS.md`. Its `--json` mode validates and checks documentation without writing. `node scripts/new-family.mjs family-id` creates an unregistered scaffold; populate verified definitions and accuracy evidence before registration.
- Preserve version-1 import support, version-2 saved projects, storage/recovery keys, published IDs and current canvas geometry. The geometry fixture guards both published version-1 anchors and reviewed physical layouts. A source audit that requires further anchor changes needs an explicit saved-project migration; preserve native asset geometry independently of canvas positions.
- Keep local serving and production packaging in the Node scripts. Test the versioned output and its module/CSS paths before release.
